# Detector evaluation

Read-only. Generated by `scripts/detector-eval.mjs`. No engine or ranking code changed.

**This is a disposable diagnostic sample, not a specification.** It is up to ten
examples from each of nine detectors, used to test whether those detectors
produce good cards. It is not the card-generation system, not the Manish design
space, and not something to preserve. The source of truth is
`docs/card-generation-spec.md` — the recovered grammar and detector vocabulary.
Regenerate or discard this file freely.

Three separate questions, which is why there are three labels:

1. **INSIGHT** — did Blueprint find something genuinely interesting to say?
2. **DISCOVERY** — does that thing lead to music worth exploring?
3. **ABSENCE RISK** — how confident are we that "missing" is an opportunity
   rather than a deliberate omission?

A detector should not be rejected because its track-opening is weak if the
observation is excellent, and a card is not excellent merely because it opens
good music if the proposition is "because you like X, here is Y".

**Absence is ambiguous evidence.** Blueprint knows saved and not-saved. It does
not know heard and unheard, or liked and disliked. Not in the library means
none of: unknown, an opportunity, or a negative preference. Every absence-based
card carries a risk field measuring that ambiguity — it is not a claim about
which explanation is true.

Give each detector a family verdict: **CORE** / **USEFUL** / **NICHE** /
**WEAK** / **REJECT**.
